# External RGB-D integration review

Reviewed the deployment design against `index.py`, `loaders.py`, `provider.py`, `preview.py`, `deployment.py`, `models.py`, and their integration/model/deployment tests. CLI/extraction orchestration was still being developed and was outside this review. No source files were edited.

## Findings

1. **P1 — Smoke can identify an explicitly marked synthetic fixture as real data.** `deployment.py:216–240` reads any existing index, never checks `sample.metadata.sample_provenance`, and unconditionally writes `source: real_dataset`. Reproduction: use `tests/test_external_rgbd_robomind.py::_trajectory` (which writes the HDF5 `synthetic_fixture=True` attribute), discover its rows, call `build_index`, then call `smoke_dataset`. It succeeds with `{"source": "real_dataset", "samples": 2}`. `validate_dataset` has a fixture rejection, but the independently callable smoke command does not. Require provenance validation before a real smoke report, or report fixture execution in an explicitly separate channel.

2. **P2 — File-level RoboMIND quarantine is discarded by deployment discovery.** `deployment.py:145–147` invokes `discover_robomind_samples` without the metadata object that carries its quarantine. That reader records invalid HDF5/trajectory failures in an internally created dictionary and returns only surviving rows. `validate_dataset` then initializes a fresh quarantine at line 158 and counts only returned frames at lines 180–188. Reproduction with one valid fixture and one corrupt HDF5: direct discovery with an explicit metadata object reports one quarantined trajectory; `deployment.discover` returns two valid frame rows with no quarantine record. A mixed valid/broken deployment therefore loses failed-source counts and reasons. Pass and retain the reader's discovery report, and include trajectory-level quarantine in quality output.

3. **P2 — Empty RGB is accepted and counted as valid RGB-D.** `models.py:134–156` checks RGB dimensionality/dtype/channels, but not nonzero height/width. `DatasetSample(rgb=np.empty((0, 2, 3), dtype=np.uint8), depth_raw=np.ones((1, 2), dtype=np.uint16), ...)` is accepted and reports `rgbd_decodable=True`. A raw HDF5 RGB array can reach this path through `decode_image`; deployment then admits it because it only checks that capability. Reject empty RGB alongside empty depth before computing capabilities.

4. **P2 — Robot-base capability can be true without usable depth geometry or a depth-camera transform.** `models.py:161–162` accepts any transform whose `to_frame` is `robot_base`. A sample with unknown depth units, no `K_depth`, and only an `object_model -> robot_base` transform reports `camera_geometry=False` but `robot_base_geometry=True`. This contradicts the independent geometry gate required for base-coordinate outputs. Require valid camera geometry and an explicitly supported depth-camera-to-base transform chain.

5. **P2 — Episode basename collisions can merge different task files into one time window and index identity.** `loaders.py:49–50` groups by dataset, episode basename, camera and split; `index.py:13–17,60` likewise omits task/source trajectory identity. RoboMIND discovery stores the task and episode basename separately. Reproduction: two rows from `task_a.h5` and `task_b.h5`, with the same `episode_id`, consecutive frame indices and the same split, produce a length-two window containing both tasks. Use the complete canonical trajectory identity consistently for grouping, sample IDs and windows; include revision when mixed revisions are supported. No evidence promises globally unique episode basenames across task directories.

## Verification

All are small offline/synthetic software checks, not real deployment acceptance.

Executed temporary `PYTHONPATH=src .venv-data/bin/python` probes using only clearly synthetic test fixtures. Confirmed all five outputs described above. Temporary directories were cleaned automatically; no fixture data was added to a real data root.

The reviewed normal paths preserve official split fields, detect group/content conflicts, avoid crossing missing frame indices, collate different image sizes and nullable fields, bound worker submission to the current batch, keep GT/action fields out of ordinary observations, reject hardware mode, preserve original timestamps, and label unknown depth units honestly in previews. These existing tests do not cover the five failure paths above. CLI missing functionality was not treated as a finding.
