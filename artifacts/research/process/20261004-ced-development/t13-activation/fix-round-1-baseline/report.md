## Interfaces and semantics

- initialize_retry_budget_if_absent(RecoveryBudget) -> RecoveryBudget is on the protocol and both repositories. Memory holds its lock; SQLite holds BEGIN IMMEDIATE over lookup/insertion. An existing complete row is returned without updating any bytes, limits, counts, created/updated time or absolute deadline. All returned/input data is copied. Root's retry service consumes this producer.
- ReplanApplyRecord now carries repair_id, immutable complete candidate_contract/payload_hash, request_payload_hash and response_payload_hash, canonical checkpoint_hash, candidate/accepted/executing plan_version and command_seq, stage_attempt_id, activation_token, actual stage_ack/resume_ack and start_receipt. New states are PREPARED, EDGE_ACCEPTED, ACTIVATED, EXECUTION_STARTED, REJECTED and EXPIRED; legacy enum values remain readable diagnostics. The canonical record content hash blanks only its self-hash field; checkpoint canonical hash follows the existing same convention.
- ReplanExecutionReceipt is a strict frozen model with repair_id, task_id, plan_version, command_seq, activation_token, payload_hash, event_id and aware occurred_at. Current module repair_id equals the deterministic apply_id (apply-{request_id}). confirm_execution_started(receipt) -> ReplanApplyRecord validates current active candidate, time and exact bindings. First receipt persists EXECUTION_STARTED; exact current retries preserve the first event/time; conflicting, unknown and old-current-version receipts reject. A start event cannot be reused by another repair, including across SQLite connections/restart.
- ReplanDispatchGateway exposes stage(TaskContract, repair_id) -> actual CommandAck and resume(repair_id, activation_token) -> actual CommandAck. There is no dispatch fallback. Stage acceptance requires exact task/plan version/command, repair_id/payload_hash details, nonempty edge-supplied activation_token, ACCEPTED status and current aware timestamp. Tokens and ACKs are never fabricated. Invalid/negative actual stage responses persist as rejection evidence with accepted versions/token unset; matching negative resume ACKs remain actual nested evidence on ACTIVATED, without asserting start.
- ReplanSubmitEvidence(decision: DecisionEnvelope, current: CommitContext, action: ActionEvidenceContract, online_evidence: OnlineEvidenceSnapshot) is frozen, copies proprioceptive state and recursively freezes visual facts. submit_guard(record, candidate, current_checkpoint) returns these typed inputs, not a Boolean or caller VALID verdict. Defensive copies plus post-callback canonical hash checks reject guard mutation of record/candidate/checkpoint. The service itself calls canonical validate_decision_commit and validate_evidence with mandatory current online evidence, exact actual versions/frame/episode/calibration/sensors/error/motion/age, candidate conditions and targets, and a duration bound covering remaining candidate steps.
- update_replan_apply_record_if_current(record, expected_status=...) -> record | None performs monotonic stage/claim/resume/start CAS, protecting all immutable candidate identities and already persisted actual evidence even when model_copy or a stale declared hash is used. Public save inserts only preparation/diagnostics, and rejects altered existing content and injected stage/activation/start state. Stage_attempt_id is a coordination claim UUID, NOT an edge activation token or count of actual gateway calls. A claim can persist even when the subsequent guard blocks or transport fails; restart waits and never retries physical staging automatically.
- advance_active_contract_if_current retains its public existing inputs and adds optional replan_record and activation_guard(record, current_checkpoint, cancelled) -> EvidenceVerdict. Staged activation requires prior EDGE_ACCEPTED, exact frozen previous/current versions, same candidate bytes, current checkpoint identity/content, current task cancellation/terminal state/critical or interrupt events, and exact canonical VALID callback. Memory holds one lock; SQLite uses BEGIN IMMEDIATE and suppresses the helper's inner commit so supersede/new active/ACTIVATED record commit together. The callback must be pure and must not read/write the repository under that lock.
- apply(...) keeps its API, adding constructor submit_guard. It validates and persists PREPARED before effects. dispatch=False or missing typed guard/stage/resume capability yields a candidate, no ACK, no active advance and no READY_TO_RESUME. A once-only durable claim precedes a fresh pre-stage checkpoint/cancel/version/proof check. Actual accepted stage freezes the token; active CAS recomputes the proof; proof/cancel/checkpoint/active version are checked again before explicit resume. Resume timeout/rejection leaves ACTIVATED and waits for coordination, without rollback or automatic replay. ReplanApplyResult.applied means the active candidate was durably advanced; it does NOT mean execution began or succeeded. Resume ACK also does not imply execution start.
- LocalReplanningService.process now returns the original saved cloud response after apply. Apply-record state separately expresses candidate preparation/activation/rejection. The already-persisted response is never overwritten to masquerade as an application outcome.

This v1 module deliberately binds DecisionEnvelope/CommitContext candidate_set_hash to the complete candidate TaskContract payload hash and context_hash to the complete frozen checkpoint digest. T12's actual candidate-set/choice/context identities are distinct. Root's later adapter must preserve those identities and build an explicit choice-to-contract/context binding map with the full frozen candidate configuration. It must not replace or conflate T12 hashes. Actual mode/admission/safety/provider policy construction, live edge staging, checkpoint reconciliation, executor/completion/lifecycle integration and fresh evidence acquisition remain root-owned integration work; no caller VALID toggle substitutes for them.
