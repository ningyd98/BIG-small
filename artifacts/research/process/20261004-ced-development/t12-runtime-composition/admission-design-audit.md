# Actual runtime admission bridge: design audit

Date: 2026-10-04. Scope: read-only design audit following the independently reviewed runtime composition software. No production source changes, model calls, captures, dispatch, INITIAL freeze, selection acceptance, physical execution or recovery enablement were performed for this audit. The adapter's frozen source/manifest remain unchanged.

## Current finding

The two unconditional `actual_admission_verifier_unavailable` returns are deliberate and still necessary. Replacing them requires independently reconstructed method prerequisites **and** a current owner snapshot. A source callback, a typed request, a content hash, a saved summary or `source_accepted=true` cannot supply either proof.

The available inventory contains diagnostic/dry-run protocols and historical acceptance reports. The current stage summary explicitly records no accepted cloud-edge-device INITIAL/FINAL or actual selection/calibration acceptance. `configs/research/joint_policy.yaml` has null INITIAL/risk/weights/selection/verifier fields and `adaptive_enabled: false`; `configs/research/ced_roles.yaml` has no cloud profile and only the existing CONTINUE/REOBSERVE/STOP verification router. These are unavailable prerequisites, not grounds for selecting arbitrary values.

## Actual owner registration

`RuntimeCompositionSnapshot` checks coherence after a reader returns it; it cannot prove that its fields were read from the actual runtime. The actual reader has not been registered.

`experiments/runtime_harness.py:563` creates event/auto-mode repositories, active contracts and the existing task executor, but uses mock robot/scene providers. It is useful for software tests, not an actual RGB-D source. `_VisualEpisode` in `vision/execution.py:534` owns the actual observation, robot, tracker, absolute verification budget, versions and sole shared `SkillExecutor`, but currently has no authoritative event-repository active contract/execution checkpoint or auto-mode status registration. Its private `_state_version` is not `AutoModeStatus.mode_version`, and a skill boundary is not automatically a persisted checkpoint.

There is a further binding constraint confirmed in `run_online` (`vision/execution.py:1265`) and `resolved_step` (`:492`): the immutable compiled plan is subsequently resolved into a step with new physical parameters/timeouts and empty legacy preconditions/success conditions. The owner then constructs a different per-step `current_contract` payload under the same plan/command versions. A registry must not persist each such changed payload as another active contract with the same revision. First freeze the original canonical `ConditionSpec` requirements and their task/step/target binding separately; preserve the original planned-contract/step hashes. Bind execution grounding as a derived current intent: original step and requirement hashes, current observation/checksum/calibration/context, resolved parameters/duration and the derivation/source identity. After SafetyShield limits parameters, bind the final limited intent and recheck the native proof for that exact intent. A change outside the allowed grounding derivation requires the existing versioned replan/apply path. Empty conditions in a legacy executor view must never erase or discharge the original requirements. This ownership design is a prerequisite; no fast registration implementation is proposed.

The smallest actual owner integration is a single owner-thread registration/read seam, implemented by the vision/runtime owner after review:

1. Register the accepted original active `TaskContract` in the existing event repository; freeze its canonical semantic requirements and separate derived-grounding binding described above; register the initial `AutoModeStatus` in the existing auto repository. Bind task/episode/plan/command and the real robot identity. Missing records STOP; never synthesize current status from a default mode or old contract. Do not overwrite the same active revision with a per-step resolved contract.
2. At a verified non-atomic skill boundary, persist the exact completed prefix/current/pending step state using the existing `ExecutionCheckpoint` format and hash. Resolve `get_active_contract`, `get_latest_execution_checkpoint`/`get_checkpoint` and `AutoModeRepository.get_status` from the actual repositories. Existing APIs are under `repositories/event_autonomy/{protocol,memory,sqlite}.py`, not a new state machine.
3. Under the owner lock/serialized event loop, copy the actual observation, robot state, tracker facts, contract, checkpoint, mode, current capabilities, limits and remaining budget into the snapshot. Use one generation boundary; if observation/contract/checkpoint/mode changed during assembly, retry a bounded read or reject. Merely calling independent readers sequentially is not an atomic snapshot across the separate SQLite databases.
4. Preserve the original verification deadline and remaining counts on restart. Do not call `VerificationBudgetState.start` again for the same episode. Current T12 software charging is an in-process diagnostic mechanism and is not a durable quota transaction. Existing persistent recovery/task retry budgets remain separate; reuse their current owner mechanisms without pretending they already persist verification reobservations.
5. Pass only detached copies to contract/judge/admission callbacks. Re-read the authoritative owner generation and all current versions, cancellation/native hard stops, atomic boundary and absolute deadlines after callbacks and after audit acknowledgement. No callback receives authority to alter the actual pool or registry.

## Replacing the closed return

A proposed read-only `ResearchAdmissionRequest` identifies a registered evidence-root key, stage, method/policy/risk/weights identities and source set. Directory paths come from an explicit owner allowlist, not user query strings or callback assertions. A proposed `ResearchAdmissionAudit` reports `VALID | INVALID | UNKNOWN`, structured reasons, independently observed raw/source hashes, exact verified stage and finite candidate identity. It is diagnostic data, not a bearer token.

The adapter should invoke a concrete independently tested verifier against the registered root and current owner snapshot. The verifier must repeat byte/source and semantic binding checks when considering actual submission. An injected callback that simply returns `VALID` or a hand-made receipt must not enable a path; a receipt may cache expensive reconstruction only with the complete raw-file/configuration/source inventory key and fresh current-version/expiry checks. Cache failures must stay failures. No cached result survives changed raw bytes, omitted assigned failures, altered registered root, changed policy/config or current source drift.

Once that verifier exists and is independently reviewed, replace each unconditional closed return with its result: UNKNOWN/missing prerequisites → STOP/no submission; INVALID → STOP; VALID → continue the existing decision and commit validation. Both `JointEvidencePolicy.decide` and `RuntimeCompositionAdapter` currently close actual admission, so changing only the adapter would still leave the policy unavailable. This is a coordinated narrow integration, not a flag flip.

Even a VALID method audit must not bypass `validate_decision_commit`, the fresh complete-version check, capability/budget limits, atomic deferral or physical `validate_evidence`. A decision trace is an intent; it is not ACK, action start, physical execution or success. LOCAL_RECOVER additionally requires the independently admitted T13 source pool/module/calibration/lifecycle and remains absent until its owner provides those prerequisites.

The owner consumes an eligible intent through the existing `_VisualEpisode.execute` sequence only: immediate active/hard-stop checks and current role binding → native PRE_SAFETY evidence → SafetyShield built from the resolved current intent → native PRE_SKILL evidence → existing `SkillExecutor.execute_attempt`. At PRE_SKILL an invalidated proof stops; it never recaptures and reuses the old shield context. Recovery uses the separately existing canonical apply/activation/lifecycle route; the adapter never submits to a robot, creates another executor, sends HTTP or commits a mode transition itself.

## Smallest software work possible before external evidence

Recommended first bounded addition: one independent read-only admission auditor plus its tests, with explicit typed requests/results and owner-registered roots. It can complete original-source inventory, canonical INITIAL reconstruction/comparison, calibration raw-source auditing, finite selection manifest/schema/completeness checks and exact structured missing-evidence results. Empty/missing actual Max, calibration or selection inputs must yield UNKNOWN and no admission. All synthetic success fixtures must report SOFTWARE_ONLY and cannot satisfy the actual verifier.

Next bounded addition: a read-only repository/owner snapshot reader with generation checks, detached copies, restart identity checks and missing-record STOP. It can be tested with existing repositories and a fake owner without wiring a dispatcher or opening the actual policy. Hardware/Max-independent tests can cover duplicate/out-of-order events, mode/plan/checkpoint drift, failed read/source mutation, late callbacks, hard stops and absolute-budget preservation. Actual vision owner registration and risk acceptance integration belong to their current owners; they are not edits authorized in this audit.

A native geometric/motion certificate collector/validator can also be prepared as a separate UNKNOWN-by-default software contract, but a fixture or model reply cannot certify its physical values. Actual acquisition and independent residual acceptance remain external work. This bridge alone cannot make the currently closed native baseline run or initial freeze acceptable.

Before enabling any actual adaptive method, require a reviewed end-to-end evidence chain: registered genuine role probe/profile → all actual B0 selection/foundation/resource/opportunity/recovery evidence → independently reconstructed INITIAL → actual disjoint calibrated risk and current native bounds → finite preregistered selection exploration → complete independently accepted selection → coherent owner registration/current checkpoint/mode/budget → existing canonical/Safety submission. Missing any required link preserves the existing closed behavior.
