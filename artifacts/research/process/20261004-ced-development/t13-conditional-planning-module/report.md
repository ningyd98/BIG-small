# Conditional repair planning carrier

The additive local carrier represents future requirements while preserving their original policies. It performs no model request, budget reservation, renderer operation, capture or robot action. Only two new files are owned: `cloud/replanning/conditional_intent.py` and `tests/test_conditional_repair_intent.py`. Existing strict role provider, submission horizon, SafetyShield, SkillExecutor, repository CAS, default worker and method admission remain unchanged. Independent review is pending.

Inputs are the detached original plan/requirements, supplied current owner/checkpoint/frame/evidence data and a strict pixel-only JSON replacement intent. The module computes its repair window from the original dependency graph and current completed prefix, binds the complete original/current input data and deadline, and requires exact ordered authorized IDs and original skills. Completed and unrelated steps preserve their original JSON. Unknown/executable response fields, duplicate keys, new effect IDs, skill changes, malformed pixels and unbound/stale/foreign contexts reject.

Every original target, full condition/tolerance/sensor specification, error allowance, ordinary TTL, duration, timeout and retry policy is retained. Current canonical precondition diagnostics are recorded without promoting future FAIL/UNKNOWN to PASS. The software GRASP-to-LIFT case retains current `gripper_holding=FAIL` for LIFT as a requirement to recheck, rather than issuing LIFT authority.

`ConditionalRepairPlanningIntent` is a distinct immutable PLANNING_ONLY type with method/execution admission fixed false. It contains no executable steps collection, ActionEvidenceContract, TaskContract, activation token or submission method; its payload is rejected by strict LocalReplanningResponse validation. The returned preserved-step view and original requirement models are detached. The component reuses exact frozen owner validation/hash helper sources, but its local consistency binding does not authenticate a live lease, verify current disk sources, prove geometry or establish actual effects. A caller supplying the clock is responsible for fresh invocation; a future actual owner adapter must independently obtain and recheck these sources.

Before any physical use, each next step still needs new actual grounding, canonical precondition evidence, the unchanged full-duration submission check and existing durable owner/mode/budget CAS. The cloud adapter and durable worker integration have not been implemented by this carrier. It cannot resolve recovery, start a skill, establish METHOD or prove success.

The initial qualified missing-module run had 21 failures; its separately recorded RED log remains in the design package. First implementation passed 21 cases. Cold mypy then found a JSON getter returning untyped Any; its first source and log are preserved, and an explicit mapping check corrected the getter. Formatting/import cleanup was local to the two owned files. Final local scoped verification passed 164 tests in 1.33 seconds, covering 21 new cases and the exact 143 owner/evidence/composition/repair regressions; Ruff and cold mypy passed. No suites are summed as physical episodes.

The immutable closure is the exact independently reviewed owner package of 770 files plus the two new files. `source-hashes.json`, `ownership.json` and `review-package.diff` identify the full 772-file archive and its two owned files. Hash/AST verification passed during freeze. The package contains no moving live dependency overlay and does not accept actual research sources.
