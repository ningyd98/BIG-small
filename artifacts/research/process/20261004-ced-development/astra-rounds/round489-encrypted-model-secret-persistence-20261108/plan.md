Actual gpt-6-astra plan under AGENTS.md for the explicit request “密钥固化，不要每次重新配”. The user authorizes persistent local storage; no design-confirmation loop. **Goal:** Save future model keys once in a private encrypted local vault, recover them after ordinary process restart, and report actual storage state without exposing keys.

## Evidence and boundaries

Current SecretStore implementation is only InMemorySecretStore. API `_service` always constructs it, capabilities advertises only SESSION_ONLY, and `_with_active_flag` returns persisted secret_present/kind without consulting the store. Thus stale SQLite metadata can claim a lost session key exists. The UI explicitly warns of re-entry after every restart. These are source-confirmed issues, not an invented new execution failure; pinned source files below/plan.json are the original evidence. Parent reports current HEAD 3b2a698b with no pending source/test edits; recheck HEAD and pins before execution.

Implement standard cryptography.Fernet authenticated encryption; use no homemade crypto, plaintext key environment variable, browser storage or secret-export endpoint. [Official Fernet documentation](https://cryptography.io/en/latest/fernet/) specifies generated secret keys and authenticated decryption. The vault's master key and ciphertext are local-owner private files: this protects against accidental plaintext storage and other users, not a compromised same-user process/root. No secure-erasure or rollback-attack resistance claim.

Current live API retains the already entered key only in memory. It cannot be migrated through an existing supported interface. Do not inspect/extract process memory/environment, relay profiles, restart, hot-patch or add export. Prepare and verify persistence without touching that service or the user's vault; explain one final entry through the existing write-only UI after a later controlled deployment. No model calls, render/GPU/controller/physics work in this plan. Preserve R488 trusted-calibration rules and paid-call gate.

## Vault requirements

1. Constructor/factory is lazy: absent vault directory on read returns no secret without creating files. First write creates private directory0700, persistent lock0600 and initial master/key ciphertext; master generated by Fernet.generate_key. Existing nonempty/incomplete state is never silently reset. If ciphertext exists but master is absent/wrong/corrupt, or master exists without ciphertext after an interrupted initialization, all operations fail closed. An absent directory is an empty store; deletion of the entire vault cannot be distinguished from a new installation, and derived metadata must say absent.
2. Validate directory owner=euid and mode0700, regular master/ciphertext/lock owner=euid, mode0600, link count1; reject rather than chmod insecure existing files. Refuse symlink directory/file components and unsafe nonregular files. Traverse/anchor the configured path with directory FDs and O_NOFOLLOW; validate fstat on opened descriptors, not only a pre-open exists check. Root-owned ancestors are allowed; configured vault and its replace-capable parent must not be writable by other users (allow sticky /tmp traversal to private tmp_path). Do not inspect/read target bytes before structural checks. Use fresh file descriptors for operations and revalidate paths rather than caching plaintext indefinitely. No protection against an adversarial same UID is claimed.
3. Every read-modify-write holds an OS flock on the stable lock file; acquire with bounded5s wait, never unlink/replace the lock. Freshly decrypt current ciphertext inside that lock, apply exactly one map mutation, then encrypt in memory. This coordinates independent processes/instances and prevents lost updates; reads use the same locking discipline. Hold lock through write/fsync/replace/directory fsync. Do not retain an old decrypted map across operations.
4. Write only encrypted bytes to an exclusive0600 temporary file in the same opened directory; fsync it, atomic os.replace it over vault.fernet, fsync directory before acknowledging success. Master creation is exclusive and synced; never regenerate existing master. Initialization's key/token pair cannot be atomically committed together, so interrupted partial initialization remains a reported blocked state, not auto-recovery. Delete/rotation replace encrypted map, never rewrite master. Cleanup only the current operation's own temporary ciphertext file. On failure preserve prior valid ciphertext where possible; after replace but failed fsync report failure/uncertain durability, no false durable-success acknowledgement. No secret contents in debug/repr/assertion diagnostics.
5. Exact ignores: `**/.model-control-secrets/`, `**/master.key`, `**/vault.fernet`, `**/vault.lock`, `**/.vault-*.tmp`. Default data/dashboard paths are covered; arbitrary configured directory retains these fixed names. Never commit or attach real master/ciphertext/temp bytes, even though encrypted. No backup/export feature in this round.

## Service, API and UI behavior

API `_service` uses create_secret_store(database_path); an existing injected app-state service remains respected. Capabilities advertises implemented `[ENCRYPTED_FILE, SESSION_ONLY]`, without implying the current live service has migrated. Add no response field or new credential API.

`_with_active_flag` derives secret_present from secret_store.has_secret(profile_id) and kind from the actual store on every returned profile. Apply this projection to create/update results as well as get/list. A session-only store reopened empty must report false despite SQLite's old true; an encrypted store reopened with a valid entry must report true. Corrupt store must report safe failure, not false absence. api_key remains None in all model/repository/API serialization. Keep runtime READY semantics unchanged; it is not proof of a configured credential.

Secret writes complete before returning successful create/update. Blank patch deletes; omitted api_key leaves the actual secret alone. Delete secret before deleting profile metadata so vault deletion failure does not conceal an undeleted credential behind removed metadata. Do not claim a joint SQLite/vault transaction: if a later DB write fails, the store remains authoritative and subsequent derived reads reflect actual presence. Do not add blind rollback that could overwrite a concurrent rotation. Record sanitized failure and retain recoverable nonsecret metadata as existing operations permit.

UI successful save clears password as today. Branch notice and table status on returned secret_present/kind: ENCRYPTED_FILE+present says “密钥已加密保存在本机，服务重启后可继续使用”; SESSION_ONLY+present keeps current restart/re-entry wording; absent says “未配置 API Key”; unknown kind says only configured without persistence promise. Failure keeps input, displays existing generic safe message, never renders returned error bodies or writes local/sessionStorage. No prefill/readback of existing key. A persisted kind alone without present does not claim a key was saved.
